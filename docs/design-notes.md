# 设计说明：记忆、检索与可靠交付

本文按一次对话的数据流拆解：上下文如何组装、记忆如何写入、候选如何排序、后台任务如何恢复、事件如何送达客户端。

---

## 一、长期记忆流水线

### 1.1 数据分层

一条记忆就叫 **Memory**（记忆：从一段对话里提炼出的一句结论）。Episode 是证据，Memory 是结论；检索和拼 Prompt 都用 Memory，因为原文太长太碎。

| 实体 | 存储 | 含义 | 关键性质 |
| --- | --- | --- | --- |
| Episode（对话窗口） | Mongo `pet_episodes` | 一段对话窗口的原始记录 | 只追加；窗口指纹唯一索引防重复抽取；`summary` 只给人看，不参与召回 |
| Memory（记忆） | Mongo `pet_memories` | 从原文提炼的一句话结论 | 只追加；`memory_id / user_id / pet_id / viewpoint / owner / content / importance / confidence / metadata / created_at` |
| Source（出处边） | Mongo `pet_memory_sources` | Memory ↔ Episode 多对多 | 唯一键 `(memory_id, episode_id)`；支持数 = `count` |
| Stats（状态旁路） | Mongo `pet_mem_stats` | 可变状态单独放，不改 Memory 本体 | `memory_id / use_count / last_used_at / pinned / deleted_at` |
| 索引投影 | Qdrant | 由 Memory 生成的向量索引 | 可删除、可重建；重建时过滤墓碑 |

`Memory.metadata` 里放三类信息：`refutes`（它否定了哪条旧记忆）、`objective_memory_ids`（主观记忆锚定的客观记忆）、`evidence_turns`（证据落在第几轮）。**没有** `status / version / valid_from / valid_to / CAS`（比较并交换）——旧记忆永不修改。

写入链路：

```
对话窗口 → Episode → 候选 Memory → 代码校验 → 同泳道消解
→ Memory + Source 落库 → 向量投影 → 使用统计
```

覆盖是不可逆的。用户今天说"团子怕打雷"，明天说"团子现在不怕了"，如果直接改掉旧记录，就失去了"它曾经怕过"这条信息，也无法解释宠物的认知为什么变化。因此 Memory 只追加，变化用"新增一条 + `refutes` 指向旧记录"表达。

### 1.2 写入时机与三层幂等

回复结束、执行副作用清单（outbox：待办清单）时触发写入任务。待写窗口在 `pet_write_tasks` 累积，满足任一条件才成批写入：

1. 攒够 3–10 轮；
2. 用户停聊 30–120 秒（空闲防抖）；
3. 最长等待 2–5 分钟；
4. 退出、切换宠物立即写；
5. 到达模型调用预算上限。

同一用户串行、不同用户并行。串行是为了避免两条并发抽取对同一批记忆都判 `NEW`。

九步主链：

```
AdvanceTurn（固化本批轮次范围）
→ PersistEpisode（原文只写第一版）
→ Extract（LLM 出候选）
→ Validate（代码校验）
→ Reconcile（同泳道召回 + 三判定）
→ Commit（按判定落库，只追加）
→ LinkSources（记忆 ↔ Episode）
→ Project（写 Qdrant）
→ Report（写报告）
```

三层幂等，只做一层不够：

| 层 | 键 | 防什么 |
| --- | --- | --- |
| 任务层 | `external_idempotency_key` / task id | 同一业务动作重复投递 |
| Episode 层 | 窗口指纹唯一索引 | 整段对话被重复抽取 |
| 内容层 | `MD5`（内容指纹）`(record_kind + viewpoint + text)` | 同一条记忆重复写入 |

### 1.3 抽取：模型只提议，代码说了算

模型输出候选 Memory，不直接写库。系统在落库前做五道校验：

1. **归属收敛**：客观记忆 `owner` 固定为 `world`；主观记忆只能归属当前 `user_id` / `pet_id`。
2. **内容约束**：一条不超过 50 字、只表达一个语义单元；客观用第三人称、可核验，主观用第一人称（"我知道主人去了杭州，有点想他"）。
3. **证据约束**：`evidence_turns` 必须落在本批窗口内，不能引用窗口外的轮次。
4. **重要度收敛**：模型按锚点档位给建议（0.2 闲聊 / 0.5 一般偏好 / 0.8 重要关系承诺 / 0.95 身份级），代码 `clamp`（夹到区间内）到 `[0,1]`，写入后不再改。
5. **部分成功**：合法条目继续提交，非法条目只丢该条，不让整批失败。

这段对话确实没有可记的内容时，返回空列表是**合法零结果**，不是失败。值得记的是稳定偏好、重要关系、承诺、重大事件、能力 / 身份变化；不值得记的是寒暄、一次性措辞、模型猜测、无证据的心理诊断。

### 1.4 消解：三种判定

每条候选只与**同一条泳道**（同 `user_id` + 同 `pet_id` + 同 `viewpoint`）里的旧 Memory 比较，按 `content` 向量召回 top 8 作为候选。没有候选就直接 `NEW`。

| 判定 | 含义 | 落库动作 |
| --- | --- | --- |
| `NEW` | 新记忆 | 新增 Memory + Source + 向量 |
| `DUPLICATE` | 与旧记忆等价 | Memory 不动；把本批 Episode 挂到旧 Memory（写 Source） |
| `REFUTES` | 与旧记忆冲突 | 新增 Memory，`metadata.refutes=[旧 id]`；旧记录一个字段都不改 |

执行顺序：

1. 同一泳道内内容归一化后完全一致 → 规则直接判 `DUPLICATE`，不调用模型。
2. 其余候选交给模型分类，答案空间锁死为 `NEW / DUPLICATE / REFUTES`，`target_memory_id` 必须来自本次候选白名单。
3. 模型返回不存在的 id、调用失败、或不确定 → 该条回落 `NEW`。宁可多存，不可错覆盖。
4. 已被 `refutes` 的旧记录不能再当 `DUPLICATE` 目标；命中就回落 `NEW`。

`DUPLICATE` 的支持数等于 `count(pet_memory_sources)`，不单独维护计数列。`REFUTES` 不修改旧记录，也不做状态迁移；新旧两条都在，时间线完整。

### 1.5 三条泳道与跨视角附加

| 泳道 | `viewpoint` | 含义 |
| --- | --- | --- |
| 客观 | `__world__` | 世界的共同认知 |
| 主人主观 | `user` | 主人的感受与态度 |
| 宠物主观 | `pet:<id>` | 宠物自己的理解，允许与客观不一致 |

三条泳道各自消解，绝不跨泳道。**不是每条记忆写三份**：模型判断该视角有没有独立语义才写；宠物没反应，就只有客观一条。

偏好放哪条泳道是项目判定（原文没写，标"自定"）：能脱离具体事件独立成立的（偏好、厌恶、身份、关系、习惯、承诺）放客观；必须挂在具体已发生事件上的感受、态度、期待放主观。

主观记忆用 `metadata.objective_memory_ids` 锚定客观记忆。反查"命中客观后要附加哪些主观"时，在 Mongo 上按这个字段查：

```javascript
{ "metadata.objective_memory_ids": "<客观 id>" }
```

这个字段必须建多键索引，否则反查会退化成全表扫描。跨视角只附加、不参与排序，数量上限 5。

### 1.6 纠正与删除

**纠正**：记忆页走 `REFUTES`，新增一条，`metadata.refutes=[旧 id]`；旧记录一个字段都不改。注入 Prompt 时不静默过滤旧记录，而是保留时间线并标注"已被纠正"——宠物说错话时，要能解释"我当时以为是 A，后来你说其实是 B"。

**删除**按固定顺序补偿：

1. 写墓碑：`pet_mem_stats.deleted_at = now`；
2. 删 Qdrant 向量；
3. 解 `pet_memory_sources`；
4. 清孤儿 Episode（没有任何存活 Memory 引用的原文）；
5. 最后删 Memory 本体，只保留 `memory_id + deleted_at` 墓碑。

每一步可重入、可重试；任何一步失败，补偿任务重跑不会多删。重建索引时过滤 `deleted_at != null`，删掉的记忆不能复活。清孤儿 Episode 时判断条件是"没有任何存活 Memory 引用"，不是"暂时没有 Memory"——抽取失败的 Episode 要保留，等补抽。

删除整只宠物按 `Source → Stats → Memory → 向量 → 媒体文件` 的顺序执行，先断引用再删本体。

**隔离**：每只宠物有独立记忆域。`user_id + pet_id + viewpoint` 在召回前进入 Qdrant 的 payload（随向量一起存储的过滤字段）与 BM25 语料范围，一只宠物的记忆不会进入另一只的上下文。

### 1.7 使用强化与遗忘

只有**实际被使用**的记忆才计数：Prompt 组装时写 Manifest（清单：每条记忆的 `memory_id / score / reason / used`），`used=true` 才在 Redis 上 `HINCRBY`（原子自增命令），不阻塞读路径，也不直接写 Mongo / Qdrant。Worker 每 5 分钟把计数合并进 `pet_mem_stats`。

保持度 `retention` 是**排序信号**，回答"这次召回该不该排前面"；容量淘汰是另一套决策，回答"满了先删谁"。两者不要混为一谈。容量到水位线（90%）时按保护名单处理：

- `importance >= 0.85` 不淘汰；
- 用户手动 `pin` 不淘汰；
- 承诺 / 身份 / 重要关系不淘汰；
- 被 `refutes` 的记录进归档区，不占活跃配额；
- 具体淘汰排序待评测校准。

## 二、混合检索

### 2.1 检索链路

```
用户原句 + 最近几轮
→ 查询扩展（原句必留）
→ 向量召回 top 30 ┐
→ 关键词召回 top 30 ┴→ 名次融合 k=60 → 归一化 → top 40
→ 多信号加权 → top 8 → 跨视角附加（≤5）→ Prompt
```

### 2.2 QueryExpand

宠物场景的真实问题：用户说"你还记得它吗"，原句里没有"团子"、没有"医院"、没有时间，直接搜必然召回一堆无关记忆。QueryExpand（查询扩展：把带代指的原句补全成若干检索表达）用原句 + 最近几轮做改写，输出若干个检索表达。

四条规则：

1. 空 query 不调模型、不搜；
2. 超时 3 秒，失败退回原句；
3. 原句必须保留一路，防止改写漂移；
4. 同一个 `memory_id` 只留最高分，同一个 query 只编码一次。

### 2.3 Dense 与 Sparse 双路召回

**Dense（稠密向量：把文本压成固定维度数字，语义相近则距离近）**：调用 `text-embedding-v3` 生成 1024 维向量，在 Qdrant 中按 `user_id / pet_id / viewpoint` 过滤（payload：随向量一起存储的过滤字段）后检索，每路召回 30 条。

**Sparse（稀疏关键词：按词是否出现及权重表示文本）**：在当前范围内只取未删除的 Memory 作为语料，用 BM25（经典关键词相关性打分，综合词频、逆文档频率与文档长度）打分，召回 30 条。中文 token（模型处理文本的最小计量单位）使用字符二元组，避免依赖分词词典。

BM25 公式：

```
score(D, Q) = Σ IDF(q) · f(q,D)·(k1+1) / (f(q,D) + k1·(1-b+b·|D|/avgdl))
```

参数：`k1=1.5`（词频饱和），`b=0.75`（长度归一化）；`IDF` 是逆文档频率（越少见的词，区分度越高）。

### 2.4 RRF 融合与归一化

RRF（Reciprocal Rank Fusion，倒数排名融合：只用名次换算分数再相加）：

```
RRF(d) = Σ 1 / (k + rank_i(d))
```

`k=60`，`rank` 从 1 开始。两路分数的量纲不同，直接相加没有意义；RRF 只使用名次，天然可比。

但 RRF 的原始分有上限：双通道、每路最好名次都是 1 时，`raw = 2/(k+1) = 2/61`。所以：

```
ceiling = 2 / (60 + 1)
normalized = min(raw / ceiling, 1.0)
```

归一化到 `[0,1]` 后才能和多信号加权里的其他项相加。`ceiling` 绑死"双通道"这个前提：以后加第三路召回，必须同步改成 `3/61`，否则归一化会失真。

融合后取 top 40。同一个 Memory 被多个子查询命中时，只取最高归一化分，不累加；否则改写越多，分数越高。

### 2.5 多信号加权

```
score = 1.00*语义 + 0.20*保持度 + 0.15*重要度 + 0.10*时间
排序键 (score, 语义) 降序 → 取 top 8
```

| 信号 | 来源 | 量纲 |
| --- | --- | --- |
| 语义 | Dense + BM25 两路 RRF 归一化 | `0~1` |
| 保持度 | `retention = exp(-age_days / S)` | `(0,1]` |
| 重要度 | `Memory.importance`，抽取时定 | `0~1` |
| 时间 | 与提问时间窗的匹配度 | `0~1` |

保持度的稳定天数：

```
S0 = 3 + 30*importance
boost_use      = 1 + 0.6*ln(1+u)
boost_spacing  = 1 + 0.08*min(d,5)
boost_evidence = 1 + 0.10*ln(1+e)
S = S0 * boost_use * boost_spacing * boost_evidence
age_days  = (now - (last_used_at ?? created_at)) / 86400
retention = exp(-age_days / S)
```

`u` 是实际使用次数，`d` 是不同自然日使用天数，`e` 是支持它的不同 Episode 数。使用越多、使用间隔越分散、证据越多，`S` 越大，保持度衰减越慢。`0.6 / 0.08 / 0.10` 与 `min(d,5)` 是自定参数，待评测校准。

时间信号：

- 无时间意图 → 0.5（中性，不偏向新的也不偏向旧的）；
- 有时间意图且落在窗口内 → 1.0；
- 有时间意图但在窗口外 → 按距离衰减；
- 高置信度时间查询 → 不走分数，直接硬过滤。

三个设计点：

- **语义是决定性项**：权重和是 1.45，语义占 1.00，约 69%；其余三项只做小幅修正。
- **重要度被计入两次（有意）**：既进 `S0` 影响保持度，又单独拿 0.15 权重。这是快看原文的设计，不是重复计算错误。
- **排序完全在应用内完成**：四个信号都有明确来源，结果可复算；同分时再比语义，避免重要度把不相关的记忆顶上来。

### 2.6 跨视角附加

命中客观记忆时，附加通过 `metadata.objective_memory_ids` 关联的主观记忆；命中主观记忆时，附加它锚定的客观记忆。附加项：

- 只附加，不参与主排序；
- 也要过 `user_id / pet_id` 权限；
- 数量上限 5；
- 超预算时最先丢。

### 2.7 隔离在召回前

Dense 在 Qdrant payload 上过滤；BM25 只在当前 `user_id / pet_id / viewpoint` 的 Memory 语料上打分。不会先全库召回、再在应用层筛掉别的宠物，避免越权数据进入候选集，也避免无效计算。

### 2.8 Manifest 与预算裁剪

每条进 Prompt 的记忆都记 `memory_id / score / reason / used`，回答"为什么这句进了 Prompt"，也为"实际使用计数"提供数据。

超预算时按固定顺序丢：跨视角附加项 → 已被纠正的历史条目 → 分数最低的记忆。承诺 / 身份 / 当前话题相关的不丢。

## 三、可靠异步

回复发出后，记忆抽取、三判定消解、索引投影由 Worker 异步执行。任务队列存放在 MongoDB。

### 3.1 状态机

```
pending ──claim──> running ──complete──> done
                      │
                      ├──fail（可重试）──> pending（退避后重试）
                      └──fail（不可重试）──> dead
```

### 3.2 入队幂等

每个任务携带 `idempotency_key`，MongoDB 唯一索引保证同一业务动作只入队一次。重复提交返回已有任务，不会产生第二条。

### 3.3 租约、心跳与栅栏令牌

| 机制 | 作用 |
| --- | --- |
| Lease（租约：领取任务时获得的限时工作凭证） | Worker 崩溃后任务不会永久停在 running |
| Heartbeat（心跳续租） | 按租约一半周期续期，区分"还在干活"与"已经死了" |
| Fencing Token（栅栏令牌：每次领取生成的新编号） | complete / fail / renew 都校验当前 token，旧 Worker 复活后无法提交 |

领取任务时生成新的 `lease_token`；完成、失败、续租都必须携带当前 token。旧 Worker 即使恢复，token 已经对不上，提交被拒绝。只有租约没有栅栏令牌时，旧 Worker 与新 Worker 可能同时认为自己有权提交。

### 3.4 Reconcile 对账

Reconcile（对账：定期扫描超时任务并重新入队）扫描"超过租约仍在 running"的任务，把它们放回 pending。心跳是主力，对账是兜底；两层同时存在，才能覆盖进程崩溃、网络分区、时钟漂移等不同故障。

### 3.5 Run 幂等与代次

`POST /v1/runs` 携带客户端生成的 `client_request_id`，仓储层唯一索引保证同一条消息重发只对应一个 Run（一次对话运行：从受理到终态的执行记录）。网络超时后客户端可以安全重试，不会产生两条并行对话。

同一条消息被重新生成时，Run 的 `generation`（代次）加一。每个 Proposal（提议：模型给出、尚未被系统接受的候选动作）在生成时记录当时的 generation；`settle` 校验所有提议的代次，只要有一条与当前 Run 不一致，整批拒绝。旧代次的模型结果即使晚到，也无法写入。

### 3.6 副作用幂等

每个 Effect（副作用：写库、建索引等对外部世界的改变）都带独立幂等键。即使任务被重复执行，存储层唯一索引也会挡住重复写入。同一件事做两遍，结果和做一遍一致。

## 四、流式交付

### 4.1 协议

```
POST /v1/runs              → 202 { run_id }
GET  /v1/runs/{id}/events  → text/event-stream
```

SSE（Server-Sent Events：服务器通过一条 HTTP 连接持续向下推送事件）事件包含：

| 字段 | 作用 |
| --- | --- |
| `id` | 自增序号，作为断点位置 |
| `event` | 事件类型（节点开始 / 文本增量 / 节点结束 / 终态） |
| `data` | JSON 负载 |

### 4.2 断点续传

客户端记录最后一条事件 `id`。断线重连时在请求头携带 `Last-Event-ID`，服务端从该序号之后继续推送。重连不会重放已消费事件，也不会跳过未消费事件。

### 4.3 客户端解析的三个异常输入

| 情况 | 处理 |
| --- | --- |
| 半包：一个事件被网络切成两段 | 维护文本缓冲，只在空行（事件分隔符）处切帧 |
| 中文跨片：一个汉字 3 字节，可能切在中间 | 使用流式 UTF-8 解码器，不完整的尾部字节留到下一片 |
| 心跳注释：`: ping` | 识别注释行并忽略，不当作事件解析 |

### 4.4 重连策略

- 收到真实事件 → 重试计数清零
- 指数退避：`400ms × 重试次数`，上限 2.5 秒
- 401 → 先刷新登录态，再带 `Last-Event-ID` 重连
- 服务端单连接有最长时长，到点主动重连，靠断点无缝续上

### 4.5 断线与取消

客户端断开 SSE 连接不等于任务取消。取消通过 `POST /v1/runs/{id}/cancel` 显式发起：任务在下一个可中断点退出，不再执行后续副作用，事件流标记本次以取消结束。已经写入的结果不回滚，避免回滚引入新的不一致。

## 五、流量治理

### 5.1 令牌桶

令牌桶（Token Bucket：按固定速率补充令牌，请求消耗令牌，允许短时突发）按固定速率补充令牌，请求消耗令牌；桶满后多余令牌丢弃。它既能吸收用户连续提问的突发，又有长期速率上限。

### 5.2 429 与 Retry-After

超限返回 `429 Too Many Requests` 与 `Retry-After`，明确告诉客户端等待多久。客户端按提示退避，避免无脑重试把限流变成雪崩。

### 5.3 背压

连接数、在途任务数都有上限。超过上限直接拒绝（429 / 503），而不是无限排队。排队耗尽内存会让整个进程崩溃，拒绝只影响当前请求。

### 5.4 取消

取消是"请求停止"，不是"立即停止"：正在执行的模型调用不一定能瞬间中断，但会在下一个可中断点退出，并且不再执行后续副作用。事件流明确告诉客户端"这次是取消结束的"。

## 六、上下文预算

一次对话要装入：宠物人设、近期消息、相关记忆、检索资料。全部塞入会超 token 上限，也会稀释重点。

预算按优先级分配：

1. 人设与最近几轮对话——保证"它还是它"
2. 按相关度排序的记忆与资料——能放几条放几条
3. 剩余空间留给输出

宁可少放两条记忆，也不让请求因超限被模型截断。截断不可控；预算内的裁剪是显式且可审计的，裁剪结果会记录在上下文中，便于复盘。超预算时的丢弃顺序：跨视角附加项 → 已被纠正的历史条目 → 分数最低的记忆；承诺 / 身份 / 当前话题相关的不丢。

## 七、可观测与版本冻结

- Run 创建时冻结 VersionTuple（版本四元组：流程、提示词、模型路由、索引版本的组合）。
- 每个节点写入 NodeEvent（`seq` / `node` / `type`），形成可回放的事件序列。
- 每个 Effect 携带幂等键，失败可重试且不重复。
- 任务记录保留 lease token、失败原因与重试次数。

任意一条回复都可以反查：当时跑的是哪版图、哪版提示词、哪个模型路由、哪版索引，以及它引用了哪些 Memory 与出处。
