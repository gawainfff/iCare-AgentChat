# 设计说明：记忆、检索与可靠交付

本文按一次对话的数据流拆解：上下文如何组装、记忆如何写入、候选如何排序、后台任务如何恢复、事件如何送达客户端。

---

## 一、长期记忆流水线

### 1.1 数据分层

| 实体 | 含义 | 关键性质 |
| --- | --- | --- |
| Episode | 用户说过的原话 | 只追加，永不改写，是所有结论的证据 |
| Fact | 从原话抽出的原子事实 | 可被支持、反驳、失效，不靠覆盖表达变化 |
| Profile | 按稳定维度合并出的画像 | 可重新计算，不承担权威性 |
| Provenance | 出处：每条结论对应的原始对话证据 | 任意结论都能反查到原话 |
| Index Projection | 向量 / 关键词索引 | 可删除、可重建，不是事实 |

写入链路：

```
回复生成 → 候选事实 → 冲突消解 → 事实与证据落库 → 索引投影 → 画像合并
```

覆盖是不可逆的。用户今天说「团子怕打雷」，明天说「团子现在不怕了」，如果直接改掉旧记录，就失去了"它曾经怕过"这条信息，也无法解释画像为什么变化。因此事实层只追加，变化通过状态与关系表达。

### 1.2 抽取约束

模型输出结构化候选事实，系统在落库前做四层收敛：

1. **归属收敛**：`objective`（客观世界）事实的 owner 固定为 `world`；`subjective`（主观）事实只能归属当前 `user_id` / `pet_id`。
2. **长度约束**：单条内容不超过 80 字符。
3. **字段校验**：缺失必填字段、类型不符、归属越界的条目直接丢弃。
4. **部分成功**：合法条目继续提交，非法条目不会让整批失败。

模型负责"从原话里读出事实"，系统负责"事实能不能被接受"。两者职责分离，模型输出不直接决定数据形态。

### 1.3 冲突消解

每条候选事实与已有事实的关系被约束在五个标签内：

| 标签 | 含义 | 落库动作 |
| --- | --- | --- |
| `NEW` | 新事实 | 新增事实与来源边 |
| `DUPLICATE` | 已有等价事实 | 不新增事实，把本次证据挂到旧事实上 |
| `SUPPORTS` | 同一主题的补充证据 | 挂证据，`support_count + 1` |
| `REFUTES` | 与旧事实矛盾 | 新增事实，旧事实标记为 `refuted` |
| `UPDATES` | 对旧事实的补充或细化 | 新增事实，旧事实标记为 `superseded` |

执行顺序：

1. 同一视角下内容归一化后完全一致 → 规则直接判 `DUPLICATE`，不调用模型。
2. 其余候选交给模型分类，但 `target_fact_id` 必须来自本次提供的候选白名单。
3. 模型返回不存在的 ID → 该条降级为 `NEW`。
4. 模型调用失败 → 整批降级为 `NEW`，避免因为分类器不可用而丢失事实。

`REFUTES` 与 `UPDATES` 都通过 CAS 修改旧事实状态，区别在关系边：前者表达"旧事实不成立"，后者表达"旧事实被更准确的说法替代"。历史原话与旧事实记录都保留。

### 1.4 画像合并

画像按三个维度生成：

- `identity`：它如何看待自己的身份与角色
- `preferences`：用户与宠物稳定表现出的偏好
- `relationship`：两者之间形成的关系描述

每条摘要必须引用真实存在的 `fact_ids`。允许集合是本次变更事实与旧画像已引用事实的并集；出现集合外的 ID 即判为幻觉，整条摘要拒绝写入。

画像带 `version`，写入使用 CAS（Compare-And-Swap，比较并交换：带上读到的版本号，版本不一致就拒绝）。并发合并时只有一个 Worker（后台任务进程）能提交，另一个重读后重新合并。画像与事实之间写入 `summarized_into` 边，保留"这段画像由哪些事实合并而来"。

### 1.5 纠正与删除

**纠正**：写一条反驳事实，旧事实状态变为 `refuted`，画像重算后自然变化。历史仍然保留，用户能看到"我当时是这么说的"。

**删除**：同时删除 MongoDB 权威记录与 Qdrant 投影。两步都可重试、可对账。只删权威记录会留下可搜索的投影；只删投影会在重建索引时让数据复活。

**隔离**：每只宠物有独立记忆域。检索范围在召回前收窄到当前 `pet_id`，一只宠物的记忆不会进入另一只的上下文。

## 二、混合检索

### 2.1 检索链路

```
查询 → 查询变体 → Dense 语义召回 ┐
                    ├→ RRF 融合 → 状态/时间过滤 → Rerank → 输出
        Sparse 字面召回 ┘
```

### 2.2 查询变体

对原问题生成最多 3 个变体：原句、去标点版本。每个变体分别进入 Dense 语义召回与 Sparse 字面召回，提高不同表述下的命中率；每一路、每一个变体都保留独立名次，融合阶段按来源记账。

### 2.3 Dense 与 Sparse 双路召回

**Dense（稠密向量：把文本压成固定维度数字，语义相近则距离近）**：调用 `text-embedding-v3` 生成 1024 维向量，在 Qdrant 中按 `pet_id / user_id / status` 过滤（payload：随向量一起存储的过滤字段）后检索，每路召回 30 条。

**Sparse（稀疏关键词：按词是否出现及权重表示文本）**：在当前范围内只取 active（仍然成立）事实作为语料，用 BM25（经典关键词相关性打分，综合词频、逆文档频率与文档长度）打分，召回 30 条。中文 token（模型处理文本的最小计量单位）使用字符二元组，避免依赖分词词典。

BM25 公式：

```
score(D, Q) = Σ IDF(q) · f(q,D)·(k1+1) / (f(q,D) + k1·(1-b+b·|D|/avgdl))
```

参数：`k1=1.5`（词频饱和），`b=0.75`（长度归一化）；`IDF` 是逆文档频率（越少见的词，区分度越高）。

### 2.4 RRF 融合

RRF（Reciprocal Rank Fusion，倒数排名融合：只用名次换算分数再相加）：

```
RRF(d) = Σ 1 / (k + rank_i(d))
```

`k=60`，`rank` 从 1 开始。两路分数的量纲不同，直接相加没有意义；RRF 只使用名次，天然可比。融合结果保留每一路的原始名次与分数，便于排障与复盘。

### 2.5 Rerank 精排

取融合后的前 40 条候选，调用 `qwen3-rerank` 逐条重新打分，输出最终前 5 条记忆。精排超时或失败时降级回 RRF 顺序，对话链路继续。

Rerank（精排：用更强的相关性模型对候选逐条重新打分）解决的是"召回阶段只看相似度，排序不够细"的问题；它不改变候选集合，只改变候选顺序。

### 2.6 隔离在召回前

Dense 在 Qdrant payload 上过滤；Sparse 只在当前 `pet_id / user_id` 的 active 事实语料上打分。不会先全库召回、再在应用层筛掉别的宠物，避免越权数据进入候选集，也避免无效计算。

## 三、可靠异步

回复发出后，记忆抽取、冲突消解、画像重算由 Worker 异步执行。任务队列存放在 MongoDB。

### 3.1 状态机

```
pending ──claim──> running ──complete──> done
                      │
                      ├──fail（可重试）──> pending（退避后重试）
                      └──fail（不可重试）──> dead
```

### 3.2 入队幂等

每个任务携带 `idempotency_key`，MongoDB 唯一索引保证同一业务动作只入队一次。重复提交返回已有任务，不会产生第二条。

### 3.3 租约、心跳与栅栏令牌

| 机制 | 作用 |
| --- | --- |
| Lease（租约：领取任务时获得的限时工作凭证） | Worker 崩溃后任务不会永久停在 running |
| Heartbeat（心跳续租） | 按租约一半周期续期，区分"还在干活"与"已经死了" |
| Fencing Token（栅栏令牌：每次领取生成的新编号） | complete / fail / renew 都校验当前 token，旧 Worker 复活后无法提交 |

领取任务时生成新的 `lease_token`；完成、失败、续租都必须携带当前 token。旧 Worker 即使恢复，token 已经对不上，提交被拒绝。只有租约没有栅栏令牌时，旧 Worker 与新 Worker 可能同时认为自己有权提交。

### 3.4 Reconcile 对账

Reconcile（对账：定期扫描超时任务并重新入队）扫描"超过租约仍在 running"的任务，把它们放回 pending。心跳是主力，对账是兜底；两层同时存在，才能覆盖进程崩溃、网络分区、时钟漂移等不同故障。

### 3.5 Run 幂等与代次

`POST /v1/runs` 携带客户端生成的 `client_request_id`，仓储层唯一索引保证同一条消息重发只对应一个 Run（一次对话运行：从受理到终态的执行记录）。网络超时后客户端可以安全重试，不会产生两条并行对话。

同一条消息被重新生成时，Run 的 `generation`（代次）加一。每个 Proposal（提议：模型给出、尚未被系统接受的候选动作）在生成时记录当时的 generation；`settle` 校验所有提议的代次，只要有一条与当前 Run 不一致，整批拒绝。旧代次的模型结果即使晚到，也无法写入。

### 3.6 副作用幂等

每个 Effect（副作用：写库、建索引等对外部世界的改变）都带独立幂等键。即使任务被重复执行，存储层唯一索引也会挡住重复写入。同一件事做两遍，结果和做一遍一致。

## 四、流式交付

### 4.1 协议

```
POST /v1/runs              → 202 { run_id }
GET  /v1/runs/{id}/events  → text/event-stream
```

SSE（Server-Sent Events：服务器通过一条 HTTP 连接持续向下推送事件）事件包含：

| 字段 | 作用 |
| --- | --- |
| `id` | 自增序号，作为断点位置 |
| `event` | 事件类型（节点开始 / 文本增量 / 节点结束 / 终态） |
| `data` | JSON 负载 |

### 4.2 断点续传

客户端记录最后一条事件 `id`。断线重连时在请求头携带 `Last-Event-ID`，服务端从该序号之后继续推送。重连不会重放已消费事件，也不会跳过未消费事件。

### 4.3 客户端解析的三个异常输入

| 情况 | 处理 |
| --- | --- |
| 半包：一个事件被网络切成两段 | 维护文本缓冲，只在空行（事件分隔符）处切帧 |
| 中文跨片：一个汉字 3 字节，可能切在中间 | 使用流式 UTF-8 解码器，不完整的尾部字节留到下一片 |
| 心跳注释：`: ping` | 识别注释行并忽略，不当作事件解析 |

### 4.4 重连策略

- 收到真实事件 → 重试计数清零
- 指数退避：`400ms × 重试次数`，上限 2.5 秒
- 401 → 先刷新登录态，再带 `Last-Event-ID` 重连
- 服务端单连接有最长时长，到点主动重连，靠断点无缝续上

### 4.5 断线与取消

客户端断开 SSE 连接不等于任务取消。取消通过 `POST /v1/runs/{id}/cancel` 显式发起：任务在下一个可中断点退出，不再执行后续副作用，事件流标记本次以取消结束。已经写入的结果不回滚，避免回滚引入新的不一致。

## 五、流量治理

### 5.1 令牌桶

令牌桶（Token Bucket：按固定速率补充令牌，请求消耗令牌，允许短时突发）按固定速率补充令牌，请求消耗令牌；桶满后多余令牌丢弃。它既能吸收用户连续提问的突发，又有长期速率上限。

### 5.2 429 与 Retry-After

超限返回 `429 Too Many Requests` 与 `Retry-After`，明确告诉客户端等待多久。客户端按提示退避，避免无脑重试把限流变成雪崩。

### 5.3 背压

连接数、在途任务数都有上限。超过上限直接拒绝（429 / 503），而不是无限排队。排队耗尽内存会让整个进程崩溃，拒绝只影响当前请求。

### 5.4 取消

取消是"请求停止"，不是"立即停止"：正在执行的模型调用不一定能瞬间中断，但会在下一个可中断点退出，并且不再执行后续副作用。事件流明确告诉客户端"这次是取消结束的"。

## 六、上下文预算

一次对话要装入：宠物人设、近期消息、相关记忆、检索资料。全部塞入会超 token 上限，也会稀释重点。

预算按优先级分配：

1. 人设与最近几轮对话——保证"它还是它"
2. 按相关度排序的记忆与资料——能放几条放几条
3. 剩余空间留给输出

宁可少放两条记忆，也不让请求因超限被模型截断。截断不可控；预算内的裁剪是显式且可审计的，裁剪结果会记录在上下文中，便于复盘。

## 七、可观测与版本冻结

- Run 创建时冻结 VersionTuple（版本四元组：流程、提示词、模型路由、索引版本的组合）。
- 每个节点写入 NodeEvent（`seq` / `node` / `type`），形成可回放的事件序列。
- 每个 Effect 携带幂等键，失败可重试且不重复。
- 任务记录保留 lease token、失败原因与重试次数。

任意一条回复都可以反查：当时跑的是哪版图、哪版提示词、哪个模型路由、哪版索引，以及它引用了哪些事实与出处。
